# 에이전트 팀 (Agent Teams)

## 에이전트 팀이 무엇인가요?

"여러 Claude가 하나의 **팀**처럼 협력해서 큰 작업을 처리하는 기능"

Claude 하나가 팀장(리드)이 되고, 여러 Claude를 팀원으로 불러서 각자 역할을 나눠 일합니다.
팀원끼리 직접 소통하며, 공유 작업 목록으로 진행 상황을 함께 파악합니다.

**비유:**

- 팀장이 프로젝트를 전체 관리하고 팀원에게 역할을 배분
- 각 팀원은 자기 영역에서 독립적으로 일함
- 팀원끼리 직접 소통하며 협력함
- 공유 칸반 보드로 전체 진행 상황을 확인

> 에이전트 팀은 현재 **실험(Experimental)** 기능이라고 합니다.

## 왜 필요한가요?

### 1. 서브에이전트로는 부족한 상황

서브에이전트(7장)는 작업을 맡기고 결과만 받는 구조입니다.
하지만 팀원끼리 **서로 논의하며 협력**해야 하는 작업에는 한계가 있습니다.

```
서브에이전트: "A 기능 조사 결과입니다" → 결과만 보고
에이전트 팀: "A 기능 담당자와 B 기능 담당자가 서로 논의하며 조율" → 협력
```

### 2. 여러 관점에서 동시 작업

하나의 작업을 여러 관점에서 동시에 살펴볼 수 있습니다.

**예시:**

```
기획서 검토를 3명의 팀원이 동시에:
- 팀원 A: 사용자 경험 관점에서 검토
- 팀원 B: 기술 타당성 관점에서 검토
- 팀원 C: 비즈니스 임팩트 관점에서 검토
→ 서로의 검토 결과를 참고하며 최종 피드백 정리
```

### 3. 복잡한 프로젝트 분할

대규모 작업을 팀원별로 분담할 수 있습니다.

**예시:**

```
분기 보고서 작성:
- 팀원 A: 매출 데이터 분석 담당
- 팀원 B: 경쟁사 동향 조사 담당
- 팀원 C: 고객 피드백 정리 담당
→ 팀장이 결과를 종합해서 최종 보고서 완성
```

## 서브에이전트와 에이전트 팀의 차이

서브에이전트(7장)와 에이전트 팀은 둘 다 작업을 나눠 처리합니다.
핵심 차이는 **팀원끼리 소통할 수 있느냐**입니다.

| 비교 항목        | 서브에이전트 (7장)        | 에이전트 팀                     |
| ---------------- | ------------------------- | ------------------------------- |
| **비유**         | 전문 담당자에게 일 맡기기 | 프로젝트 TF팀 구성              |
| **작업 방식**    | 일 맡기고 결과만 받음     | 팀원끼리 직접 소통하며 협력     |
| **결과 보고**    | 메인 Claude에게만 보고    | 팀원끼리 서로 공유              |
| **관리 방식**    | 메인 Claude가 직접 관리   | 공유 작업 목록으로 자율 조율    |
| **팀원 간 소통** | 불가 (메인을 통해서만)    | 가능 (직접 메시지)              |
| **적합한 상황**  | 집중된 단일 작업          | 복잡한 작업, 논의가 필요한 작업 |
| **비용**         | 낮음 (요약만 전달)        | 높음 (각 팀원이 별도 Claude)    |

**언제 어떤 것을 선택할까요?**

```
"기획서 하나를 검토해줘" → 서브에이전트 (결과만 받으면 됨)
"기획서를 3가지 관점에서 동시에 검토하고, 서로 의견을 교환해서 최종 피드백을 만들어줘" → 에이전트 팀
```

**전환 시점:**

서브에이전트를 여러 개 동시에 쓰다가 컨텍스트가 부족해지거나, 서브에이전트끼리 정보를 공유해야 할 때 에이전트 팀으로 전환.

## 에이전트 팀의 구성 요소

에이전트 팀은 네 가지 요소로 구성됩니다.

| 구성 요소                 | 역할                               | TF팀 비유      |
| ------------------------- | ---------------------------------- | -------------- |
| **팀 리드** (Team Lead)   | 전체 작업을 계획하고 팀원에게 배분 | TF팀장         |
| **팀원** (Teammate)       | 배분받은 작업을 독립적으로 수행    | TF팀원         |
| **작업 목록** (Task List) | 전체 작업의 진행 상황을 공유       | 공유 칸반 보드 |
| **메일박스** (Mailbox)    | 팀원끼리 메시지를 주고받는 시스템  | 팀 내부 메신저 |

**용어 정리:**

- **팀 리드 (Team Lead)**: 에이전트 팀에서 전체를 관리하는 메인 Claude 세션
- **팀원 (Teammate)**: 팀 리드가 생성한 별도의 Claude. 각자 독립된 작업 공간을 가짐
- **작업 목록 (Task List)**: 모든 팀원이 공유하는 할 일 목록
- **메일박스 (Mailbox)**: 팀원끼리 직접 메시지를 보내는 시스템

### 작동 흐름

```
1. 당신이 큰 작업을 Claude에게 요청
2. 팀 리드(Claude)가 작업을 분석하고 팀원을 생성
3. 각 팀원에게 역할과 작업을 배분
4. 팀원들이 독립적으로 작업 수행
5. 팀원끼리 필요하면 메일박스로 소통
6. 작업 목록에서 진행 상황 공유
7. 모든 작업이 완료되면 팀 리드가 결과를 종합
8. 당신에게 최종 결과 전달
```

## 에이전트 팀 사용하기

### 1단계: 기능 활성화

에이전트 팀은 실험 기능이라 기본적으로 꺼져 있습니다.
설정 파일에서 활성화해야 사용할 수 있습니다.

**설정 파일 (`settings.json`)에 추가:**

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

**용어 정리:**

- **settings.json**: Claude Code의 동작 규칙을 적어두는 설정 파일. 8장(Hooks)에서도 사용한 파일과 같음

### 2단계: 자연어로 팀 구성 요청

특별한 명령어 없이 Claude에게 말로 요청하면 됩니다.

**예시:**

```
당신: "이번 분기 사업 보고서를 만들어야 해.
       매출 분석, 경쟁사 동향, 고객 피드백을 각각 팀원에게 맡겨줘"

Claude (팀 리드): 팀을 구성합니다.
  - 팀원 A: 매출 데이터 분석 담당
  - 팀원 B: 경쟁사 동향 조사 담당
  - 팀원 C: 고객 피드백 정리 담당
```

팀원 수와 모델을 직접 지정할 수도 있습니다.

```
당신: "팀원 4명으로 이 작업을 나눠서 처리해줘. 각 팀원은 Sonnet 모델을 사용해"
```

### 3단계: 진행 상황 확인

에이전트 팀은 두 가지 화면 모드를 지원합니다.

**인프로세스 모드 (기본)**

하나의 화면에서 팀원들의 작업을 전환하며 볼 수 있습니다.

- **Shift+위/아래 화살표**: 팀원 간 전환
- **Enter**: 선택한 팀원의 세션 보기
- **Escape**: 팀원의 현재 작업 중단
- **Ctrl+T**: 작업 목록 보기/숨기기

**분할 화면 모드**

화면을 나눠서 여러 팀원의 작업을 동시에 볼 수 있습니다.
tmux 또는 iTerm2가 필요합니다.

```json
{
  "teammateMode": "in-process"
}
```

**용어 정리:**

- **인프로세스 (In-process)**: 하나의 화면에서 팀원을 전환하며 보는 기본 방식
- **분할 화면 (Split Panes)**: 화면을 여러 개로 나눠 동시에 보는 방식
- **tmux / iTerm2**: 터미널 화면을 여러 개로 나눠서 보는 프로그램. 개발자에게 설정을 요청하세요

### 4단계: 팀원과 직접 대화

각 팀원은 독립된 Claude 세션입니다.
팀 리드를 거치지 않고 팀원에게 직접 지시할 수 있습니다.

- **인프로세스 모드**: Shift+위/아래로 팀원을 선택한 뒤 메시지 입력
- **분할 화면 모드**: 원하는 팀원의 화면을 클릭해서 직접 대화

## 위임 모드 (Delegate Mode)

팀 리드가 직접 작업하지 않고, **오직 조율만** 하도록 제한하는 모드입니다.

```
일반 모드: 팀장이 직접 일도 하고 관리도 함
위임 모드: 팀장은 관리만 하고, 모든 실무는 팀원이 처리
```

**언제 사용하나요?**

- 작업이 많아서 팀장이 관리에만 집중해야 할 때
- 팀원들이 충분히 독립적으로 일할 수 있을 때

**활성화 방법:** 팀을 구성한 후 **Shift+Tab**을 눌러 위임 모드로 전환

## 작업 목록 (Task List)

작업 목록은 칸반 보드처럼 전체 작업의 진행 상황을 보여줍니다.

### 세 가지 상태

| 상태                      | 의미                    | 칸반 보드 비유 |
| ------------------------- | ----------------------- | -------------- |
| **pending** (대기)        | 아직 시작하지 않은 작업 | To Do          |
| **in_progress** (진행 중) | 팀원이 작업 중          | In Progress    |
| **completed** (완료)      | 작업이 끝남             | Done           |

### 작업 배분 방식

작업은 두 가지 방식으로 배분됩니다.

- **팀 리드가 직접 배분**: "이 작업은 팀원 A에게 맡겨줘"
- **팀원이 자율적으로 가져감**: 현재 작업이 끝나면 대기 중인 다음 작업을 스스로 가져감

작업 간 의존 관계도 지원합니다.
"A 작업이 끝나야 B 작업을 시작할 수 있음" 같은 순서를 자동으로 관리합니다.

**팁:**

팀 리드가 작업을 충분히 나누지 않으면, "작업을 더 작은 단위로 나눠줘"라고 요청하세요.
팀원 1명당 5~6개의 작업이 있으면 효율적입니다.

## 팀원 간 소통

팀원들은 메일박스를 통해 직접 메시지를 주고받을 수 있습니다.
팀 리드를 거치지 않아도 됩니다.

**예시:**

```
팀원 A (매출 분석): "팀원 B에게: 경쟁사 C의 가격 정보가 필요해요"
팀원 B (경쟁사 분석): "팀원 A에게: 경쟁사 C의 가격은 월 39,000원입니다"
→ 팀 리드를 거치지 않고 직접 소통
```

메시지 방식은 두 가지입니다.

| 방식          | 설명                      | 언제 사용하나요?                 |
| ------------- | ------------------------- | -------------------------------- |
| **message**   | 특정 팀원 한 명에게 전달  | 특정 팀원에게만 정보가 필요할 때 |
| **broadcast** | 모든 팀원에게 동시에 전달 | 전체 공지가 필요할 때            |

> broadcast는 모든 팀원에게 전달되므로 비용이 많이 듭니다. 꼭 필요한 경우에만 사용하세요.

## 계획 승인 (Plan Approval)

복잡하거나 위험한 작업은 팀원에게 **먼저 계획을 세우게 한 뒤 승인**할 수 있습니다.

```
당신: "팀원을 만들어서 인증 모듈을 리팩토링해줘.
       변경 사항을 적용하기 전에 계획 승인을 받도록 해줘"

(팀원이 계획을 세움)
팀 리드: 팀원의 계획을 검토하고 승인 또는 반려
→ 승인되면 팀원이 실제 작업을 시작
→ 반려되면 팀원이 피드백을 반영해서 계획을 수정
```

팀 리드의 승인 기준을 지정할 수도 있습니다.

```
당신: "테스트가 포함된 계획만 승인해줘"
당신: "기존 구조를 크게 바꾸는 계획은 반려해줘"
```

## 팀 종료하기

### 팀원 종료

특정 팀원만 종료할 수 있습니다.

```
당신: "매출 분석 팀원을 종료해줘"
Claude (팀 리드): 해당 팀원에게 종료 요청을 보냅니다.
```

팀원은 종료 요청을 수락하거나, 이유를 설명하고 거절할 수 있습니다.

### 팀 전체 정리

모든 작업이 끝나면 팀 리드에게 정리를 요청하세요.

```
당신: "팀을 정리해줘"
```

> 반드시 **팀 리드**를 통해 정리하세요. 팀원이 정리하면 리소스가 제대로 정리되지 않을 수 있습니다.
> 정리 전에 모든 팀원을 먼저 종료해야 합니다.

## 실제 사용 예시

### 예시 1: 분기별 사업 보고서 작성

**상황:** 분기별 사업 보고서를 작성해야 하는데, 매출 분석/경쟁사 동향/고객 피드백을 각각 조사해야 함

```
당신: "이번 분기 사업 보고서를 만들어줘.
       매출 분석, 경쟁사 동향, 고객 피드백을 각각 팀원에게 맡기고,
       최종 보고서로 종합해줘"

Claude (팀 리드): 팀을 구성합니다.
  팀원 A → 매출 데이터 분석
  팀원 B → 경쟁사 동향 조사
  팀원 C → 고객 피드백 정리

(각 팀원이 독립적으로 작업)

팀원 A → 팀원 B에게: "매출 하락 구간이 경쟁사 프로모션 시기와 겹치는데, 관련 정보 있어?"
팀원 B → 팀원 A에게: "경쟁사 X가 3월에 30% 할인 프로모션을 했어요"

(모든 팀원 작업 완료)

Claude (팀 리드): 세 팀원의 결과를 종합해서 최종 보고서 작성 완료
```

**포인트:** 팀원끼리 직접 소통해서 더 정확한 분석이 가능합니다.

### 예시 2: 기획서 다각도 검토

**상황:** 새로운 기능 기획서를 여러 관점에서 동시에 검토하고 싶음

```
당신: "이 기획서를 팀으로 검토해줘.
       사용자 경험, 기술 타당성, 비즈니스 가치를 각각 검토하고
       서로 의견을 교환해서 최종 피드백을 만들어줘"

Claude (팀 리드): 3명의 검토 팀원을 구성합니다.
  팀원 A → 사용자 경험 관점 검토
  팀원 B → 기술 타당성 관점 검토
  팀원 C → 비즈니스 가치 관점 검토

팀원 A: "이 기능의 사용 흐름이 5단계인데, 3단계로 줄여야 합니다"
팀원 B → 팀원 A에게: "3단계로 줄이려면 A와 B 과정을 합쳐야 하는데, 기술적으로 가능합니다"
팀원 C: "이 기능의 예상 전환율은 15%로 투자 대비 효과가 높습니다"

Claude (팀 리드): 최종 피드백 정리
- 사용자 경험: 5단계 → 3단계로 간소화 권장 (기술적으로 가능 확인됨)
- 기술 타당성: 구현 가능, 예상 소요 기간 2주
- 비즈니스 가치: 예상 전환율 15%, ROI 긍정적
```

**포인트:** 각 관점의 검토자가 서로 의견을 교환해서 실현 가능한 피드백이 나옵니다.

### 예시 3: 경쟁 가설 검증

**상황:** 매출이 떨어진 원인을 여러 가설로 동시에 조사하고 싶음

```
당신: "이번 달 매출이 20% 떨어졌어.
       가능한 원인을 각각 팀원에게 맡겨서 동시에 조사해줘.
       팀원끼리 서로 반론하면서 가장 유력한 원인을 찾아줘"

Claude (팀 리드): 3가지 가설로 팀을 구성합니다.
  팀원 A → 가설 1: 경쟁사 가격 인하 영향 조사
  팀원 B → 가설 2: 계절적 수요 변동 분석
  팀원 C → 가설 3: 최근 UI 변경에 따른 이탈 분석

(각 팀원이 독립적으로 조사하며 서로 반론)

팀원 B → 팀원 C에게: "UI 변경 시점과 이탈 시점이 정확히 일치하나요?"
팀원 C → 팀원 B에게: "UI 변경 3일 후부터 이탈률이 12% 증가했습니다"

Claude (팀 리드): 조사 결과 종합
  - 가설 1: 경쟁사 가격 인하 → 영향 있음 (약 8% 이탈 추정)
  - 가설 2: 계절적 수요 → 영향 미미
  - 가설 3: UI 변경 → 영향 있음 (이탈률 12% 증가)
  → 주요 원인: UI 변경 + 경쟁사 가격 인하의 복합 효과
```

**포인트:** 팀원끼리 서로 반론하면서 검증하므로, 한 명이 조사할 때보다 더 정확한 결론을 얻습니다.

## 에이전트 팀 전용 Hook

에이전트 팀에서 사용할 수 있는 전용 Hook이 있습니다.
8장(Hooks)에서 설명한 것과 같은 방식으로 설정합니다.

| Hook              | 언제 실행되나요?                | 활용 예시                     |
| ----------------- | ------------------------------- | ----------------------------- |
| **TeammateIdle**  | 팀원이 작업을 마치고 쉬려 할 때 | "다른 작업이 남아있는지 확인" |
| **TaskCompleted** | 작업이 완료 상태로 변경될 때    | "완료 조건을 충족했는지 검증" |

- `TeammateIdle`: 종료 코드 2를 반환하면 팀원에게 피드백을 보내고 계속 일하게 합니다
- `TaskCompleted`: 종료 코드 2를 반환하면 완료를 막고 피드백을 보냅니다

## 현재 제한 사항

에이전트 팀은 실험 기능이라 다음과 같은 제한이 있습니다.

1. **세션 재개 불가**: 팀원이 작업 중일 때 세션을 닫으면 이어서 작업할 수 없습니다
2. **작업 상태 지연**: 작업 목록의 상태가 실시간으로 반영되지 않을 수 있습니다
3. **종료 지연**: 모든 팀원을 종료하는 데 시간이 걸릴 수 있습니다
4. **1팀만 가능**: 하나의 세션에서 하나의 팀만 운영할 수 있습니다
5. **중첩 불가**: 팀원이 또 다른 팀을 만들 수 없습니다
6. **리드 고정**: 팀 리드를 중간에 바꿀 수 없습니다
7. **분할 화면 제한**: 분할 화면 모드는 tmux 또는 iTerm2가 필요합니다. VS Code 터미널에서는 지원되지 않습니다

## 실무 활용 팁

### 팀원에게 충분한 맥락을 주세요

팀원은 독립된 작업 공간에서 일합니다.
작업을 맡길 때 배경 정보와 목표를 명확히 전달하세요.

```
나쁜 예: "매출 분석해줘"
좋은 예: "2024년 1분기 매출 데이터를 분석해서, 전년 동기 대비 증감률과 상위 5개 제품을 정리해줘"
```

### 작업 크기를 적절하게 나누세요

- 너무 작은 작업 → 팀을 구성하는 것이 비효율적
- 너무 큰 작업 → 팀원 하나가 너무 오래 걸림
- 적절한 크기 → 한 팀원이 독립적으로 완료할 수 있는 분량

### 리서치/검토 작업부터 시작하세요

에이전트 팀이 처음이라면 파일 수정 없이 **조사/검토만 하는 작업**부터 시도하세요.
여러 팀원이 같은 파일을 동시에 수정하면 충돌이 발생할 수 있습니다.

### 파일 충돌을 피하세요

여러 팀원이 같은 파일을 동시에 수정하면 문제가 생길 수 있습니다.
각 팀원이 서로 다른 파일이나 영역을 담당하도록 지시하세요.

### 팀원이 끝날 때까지 기다리세요

팀 리드가 팀원의 작업이 끝나기 전에 직접 작업을 시작할 수 있습니다.
이럴 때는 "팀원들이 작업을 마칠 때까지 기다려줘"라고 요청하세요.

### 비용에 유의하세요

각 팀원이 별도의 Claude 세션을 사용하므로 비용이 많이 듭니다.
간단한 작업은 서브에이전트를, 복잡한 협업이 필요한 작업에만 에이전트 팀을 사용하세요.

## 용어 정리

| 용어                          | 설명                                              |
| ----------------------------- | ------------------------------------------------- |
| **에이전트 팀 (Agent Teams)** | 여러 Claude가 팀으로 협력하는 기능                |
| **팀 리드 (Team Lead)**       | 팀을 관리하는 메인 Claude 세션                    |
| **팀원 (Teammate)**           | 팀 리드가 생성한 별도의 Claude                    |
| **작업 목록 (Task List)**     | 모든 팀원이 공유하는 할 일 목록                   |
| **메일박스 (Mailbox)**        | 팀원끼리 메시지를 주고받는 시스템                 |
| **위임 모드 (Delegate Mode)** | 팀 리드가 조율만 하고 실무는 팀원이 처리하는 모드 |
| **인프로세스 (In-process)**   | 하나의 화면에서 팀원을 전환하며 보는 방식         |
| **분할 화면 (Split Panes)**   | 화면을 나눠서 여러 팀원을 동시에 보는 방식        |
| **실험 기능 (Experimental)**  | 아직 완성되지 않아 테스트 중인 기능               |
| **tmux / iTerm2**             | 터미널 화면을 나누는 프로그램                     |
